Preamble

  • This presentation is heavily based on this Confluence page I have written.
  • The nitty gritty details on the configurations for the GRTeclyn CI on the CSD3 A100s can be found in this Confluence page.
  • I won’t go through how to set everything up step-by-step, but I will give an overview of the setup which should be enough information to determine whether something similar would be suitable for your projects.
  • There are definitely other ways of setting this up, but this is what we do for GRTeclyn.

Why run CI on CSD3?

Free GitHub/GitLab/<other provider> CI minutes on ephemeral cloud runners are great but may not meet the CI needs of your project:

  • No or limited [free] GPU minutes.
  • Cannot test CPU microarchitecture-specific codepaths (e.g. AVX-512).
  • Cannot test MPI with true distributed memory and a high-speed interconnect.
  • Performance regression testing on these cloud runners is unreliable.
  • Cloud runners may be too small or too slow for your use case.
  • Cannot test on exactly the same software stack and environment as CSD3.

Limitations

This solution can benefit some projects but may not work for others because of the following limitations:

  • Security considerations mean you may have to limit who can trigger pipelines/who has write access to the repository.
  • Maintenance overhead of keeping the runner host up-to-date and secure.
  • CI pipelines will use up allocations and, when allocations end, will no longer work.
  • You will have to wait in the queue when submitting jobs to the compute nodes. Not as quick as cloud runners.
  • CI pipelines will fail when CSD3 is down for maintenance.

Overview

Code Repository

UIS GitLab Instance

  • UIS has a GitLab instance
    • Good place to host repositories
    • Permissions within RCS are already configured correctly.
    • If you leave, someone in the RSE team will still have access to the repository and CI configuration.
  • Adding a self-managed GitLab runner requires Maintainer permissions
    • Most RSEs that create projects under the RSE subgroup will only be given Developer permissions by default.
    • You will need to request a permissions upgrade.

External repository mirroring

  • GitLab CI/CD for GitHub repositories is a supported use-case.
  • Mirroring other external repositories is also supported.
  • ⚠️ Security: anyone with write access to the repository can trigger a pipeline which will run on CSD3.
    • Keep repository write permissions limited to trusted individuals.
    • Set codeowners for GitLab CI config files.
    • Consider using protected branches.
  • ℹ️ Limitation: GitHub pull requests from fork repositories will not trigger a pipeline.
    • This is the main security constraint that enforces the above.
    • Mannual pipeline approval from forks is not currently supported.

GitLab CI Infrastructure

Host server/VM

  • The GitLab Runner can be hosted on any supported server.
    • If RSE involvement in a project is short-term, consider using the research group’s own resources (or ask them to obtain some).
  • If RSE involvement in a project is expected to be long-term, you can consider using Arcus (RCS OpenStack cloud) to host runner VMs.
    • Request access to the rse-dev project in Arcus (if not in it already).
    • Create an instance under this project via the Horizon web interface.
    • Create a separate network and router per instance for isolation.
    • You may need to open a support ticket to increase resource quotas for the RSE project in Arcus:
      • Instances, floating IPs, networks, routers
    • You will need to keep this VM up-to-date.

GitLab Runner

  • Install GitLab Runner on the host server.
  • Register the runner: executor type is chosen at registration:
    • SSH executor — runs jobs directly on CSD3 via SSH; simplest approach.
    • Shell executor — runs on host, SSHs to CSD3 manually in the script
      • Required if you need to upload artifacts to GitLab.
  • Runner config stored at /etc/gitlab-runner/config.toml
    • You can have multiple runners with different configurations on the same host.
    • Runners can have tags and jobs can specify which runner to use based on these tags.

GitLab CI workflow

  • .gitlab-ci.yml – similar concept to GitHub Actions .github/workflows/ (see documentation).
  • ℹ️ SSH executor limitation: cannot share artifacts between jobs
    • gitlab-runner must be present on the remote system to do this
    • Workarounds:
      • Use a single stage to build and run the code.
      • Store any build artifacts in a shared location on CSD3 (e.g. RDS) and retrieve them in later jobs.

CSD3

Service Accounts

  • CSD3 service accounts are exempt from MFA – required for non-interactive CI use.
  • Request via a support ticket with:
    • Name, username, purpose
    • SSH public key (generated on the runner host, no passphrase)
    • IP address to connect from (the Arcus floating IP)
    • SLURM accounts and RDS storage (CC the relevant PIs)
  • ℹ️ Service accounts cannot launch interactive shells

    • Must provide a command directly to ssh, e.g.:

      ssh<user>@login-icelake.hpc.cam.ac.uk echo "Hello World!"

Tips and gotchas

  • Similar to when using CSD3 as a normal user, you can build code on the login nodes but should run it on the compute nodes by submitting a job to SLURM.
  • You can use --qos=INTR to request maximum priority (with the usual limits). If you have multiple pipelines running concurrently, you will need to ensure that they don’t submit jobs simultaneously (e.g. use lock files).
  • Use the -W flag for sbatch to wait for completion and return exit code.
  • NFS mounts (e.g. home directories) are not instantly consistent between nodes:
    • Write on compute node might not be visible on login node immediately after job completion.
